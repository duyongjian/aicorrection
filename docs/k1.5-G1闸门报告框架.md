**口径说明（认可率 M1）**：
- **主分母**：`rated_count` = `rate_action IS NOT NULL` 的归因行（用户已表态：approve/inaccurate/report）。认可率 = 其中 `approve` 的占比。
- **替代分母**：全部归因 `COUNT(*) WHERE is_mock=0 AND is_internal=0`（含未评价行）。该分母会让认可率被"沉默的大多数"稀释，数值偏低；**闸门以 `rated_count` 为权威分母**，替代分母仅作对比参考，差异需在报告中说明。
- 与看板 `dashboardService.computeM1` 的差异：看板用 `analytics_events`（`loop_attr_show`/`attr_rate`）并按 `loop_id` 去重做 loop 级口径；**闸门以 `attributions` 表行级 `rate_action` 为单一事实源**。两者可能因"一 loop 多归因"或埋点丢失而不同，正式放行以本表口径为准。

## 2. SQL 参考段

> 通用过滤：`WHERE is_mock = 0 AND is_internal = 0`。
> 引擎：better-sqlite3（SQLite）。**无内置 PERCENTILE**；p50 用有序查询。JSON 用 `json_extract`（SQLite JSON1，better-sqlite3 默认支持）。

### 2.1 认可率（M1）

```sql
-- 权威口径：attributions 行级 rate_action
SELECT
  SUM(CASE WHEN rate_action = 'approve' THEN 1 ELSE 0 END)        AS approve_count,
  SUM(CASE WHEN rate_action IS NOT NULL THEN 1 ELSE 0 END)        AS rated_count
FROM attributions
WHERE is_mock = 0 AND is_internal = 0;
-- 认可率 = approve_count * 1.0 / rated_count

-- 替代分母（对比用，非闸门口径）
-- SELECT COUNT(*) AS total_attr FROM attributions WHERE is_mock=0 AND is_internal=0;
```

### 2.2 Wilson 95% 置信下界（M2）

公式（z = 1.96，95% 置信）：

```
p_hat   = x / n
lower   = ( p_hat + z²/(2n) − z·√( p_hat·(1−p_hat)/n + z²/(4n²) ) ) / ( 1 + z²/n )
```

- `x` = `approve_count`，`n` = `rated_count`。
- better-sqlite3 若编译带 `SQLITE_ENABLE_MATH_FUNCTIONS`（多数发行版带），可用纯 SQL；否则在报告脚本（Node/TS）中按上式计算。

```sql
-- 纯 SQL（需 SQLite 数学函数；否则取 x/n 在代码里算）
WITH cte AS (
  SELECT
    SUM(CASE WHEN rate_action = 'approve'      THEN 1 ELSE 0 END) AS x,
    SUM(CASE WHEN rate_action IS NOT NULL      THEN 1 ELSE 0 END) AS n
  FROM attributions
  WHERE is_mock = 0 AND is_internal = 0
)
SELECT
  CASE WHEN n = 0 THEN NULL ELSE x * 1.0 / n END AS p_hat,
  n,
  CASE WHEN n = 0 THEN NULL ELSE
    ( x * 1.0 / n + 1.96*1.96/(2.0*n)
      - 1.96 * sqrt( x*1.0/n * (1 - x*1.0/n)/n + 1.96*1.96/(4.0*n*n) ) )
    / (1 + 1.96*1.96/n)
  END AS wilson_lower_95
FROM cte;
```

### 2.3 三项齐全率（M3）

```sql
SELECT
  COUNT(*) AS total,
  SUM(CASE
        WHEN (cause IS NOT NULL AND knowledge_point IS NOT NULL AND essence IS NOT NULL)
          OR (knowledge_point_id IS NOT NULL AND cause_id IS NOT NULL)
        THEN 1 ELSE 0 END) AS complete_count
FROM attributions
WHERE is_mock = 0 AND is_internal = 0;
-- 三项齐全率 = complete_count * 1.0 / total
```

> **讲解模式（无作答）注意**：无作答时 `cause` 被填入占位串 `'（未提供作答，已给出本题讲解）'`（非空），故"三项"在该模式实为 `knowledge_point` + `essence` 非空 + 结构化 `knowledge_point_id`/`cause_id`。SQL 的 OR 条件已兼容；报告需标注讲解模式占比，避免把占位 `cause` 误判为真实错因。

### 2.4 p50 归因延迟（M4，有序查询）

```sql
-- better-sqlite3 无 PERCENTILE：用有序查询取中位数位置
WITH lat AS (
  SELECT attr_latency_ms AS ms
  FROM attributions
  WHERE is_mock = 0 AND is_internal = 0
    AND attr_latency_ms IS NOT NULL   -- analyzing/incomplete 不落库，天然排除
),
cnt AS ( SELECT COUNT(*) AS n FROM lat )
SELECT ms AS p50_latency_ms
FROM lat
ORDER BY ms
LIMIT 1 OFFSET ( SELECT CAST(n/2 AS INTEGER) FROM cnt );

-- 如需 p95：OFFSET = CAST(n*0.95 AS INTEGER)（可选，非闸门硬性指标）
```

### 2.5 上传失败率（M5，来自 analytics_events）

```sql
SELECT
  COUNT(*) AS upload_total,
  SUM(CASE WHEN json_extract(props_json, '$.ocr_status') = 'fail' THEN 1 ELSE 0 END) AS upload_fail
FROM analytics_events
WHERE event_name = 'loop_upload'
  AND is_mock = 0 AND is_internal = 0;
-- 上传失败率 = upload_fail * 1.0 / upload_total
```

> **测量盲区与 2026-11-05 增量修复（须向干系人说明）**：
> 1. `ocr_status` 取值 `success`/`partial`/`fail`。`partial`（本地 OCR 成功 + 视觉模型合并）**不计**为失败。
> 2. **历史盲区**：传输/网络层上传失败（服务端从未创建 loop）、HTTP 4xx/5xx、HTTP 200 信封业务错误、前端校验失败**均不会**触发 `loop_upload`，因此不计入失败——M5 的分母只是「成功的 HTTP 上传」，天然偏低。**本轮已新增 `upload_fail` 诊断事件覆盖这些路径**（受控 `failure_stage` / `failure_reason` + 断网可续传的本地 outbox），设计见 `docs/上传失败细分埋点.md`。
> 3. `loop_upload` 由**客户端 SDK 在收到响应后**上报（见 `uploadService.ts` 注释），故它本质是"上传完成且已尝试 OCR"信号，而非"上传开始"信标——**v0.1 无 `upload_start` 事件**；本轮也**未**新增该事件，改用「终态互斥」（`loop_upload` 或 `upload_fail` 二选一）直接得到尝试分母。
> 4. **口径纪律（硬约束）**：M5 闸门口径（上式）**一字不改**。新增的「尝试级失败率」只是诊断指标，须与 M5 **并列**上报并标注口径不同，**禁止**用它替换 M5 去做 GO/NO-GO 判定。

#### 2.5.1 上传失败细分（新增诊断口径，非闸门指标）

```sql
-- 尝试级：终态事件互斥，故不会重复计数
SELECT
  COUNT(*) AS attempt_total,
  SUM(CASE WHEN event_name = 'upload_fail'
             OR (event_name = 'loop_upload'
                 AND json_extract(props_json, '$.ocr_status') = 'fail')
           THEN 1 ELSE 0 END) AS failure_total
FROM analytics_events
WHERE event_name IN ('loop_upload', 'upload_fail')
  AND is_mock = 0 AND is_internal = 0
  AND ts_utc >= datetime('now', '-14 days');
-- 尝试级失败率 = failure_total * 1.0 / attempt_total（通常 ≥ M5，属暴露盲区而非指标恶化）

-- 分层定位（OCR 失败 vs 传输失败的优化方向完全不同）
SELECT json_extract(props_json, '$.failure_stage')  AS stage,
       json_extract(props_json, '$.failure_reason') AS reason,
       COUNT(*) AS n
FROM analytics_events
WHERE event_name = 'upload_fail' AND is_mock = 0 AND is_internal = 0
  AND ts_utc >= datetime('now', '-14 days')
GROUP BY stage, reason ORDER BY n DESC;
```

> 已封装为 `GET /api/v1/dashboard/upload-failures?window_days=14`，响应同时给出 `m5`（原口径）与 `attempt_*`（诊断口径）+ `by_stage` / `by_reason`。完整契约与数据主权说明见 `docs/上传失败细分埋点.md`。

### 4.1 p50 耗时构成实测补充（2026-11-05，可复现）

> 上方 BLOCKER 框结论不变，本节只补**可复现实证**，把「≈110s」拆到可归因的段，
> 避免后续把工程优化误判为能解决该闸门。
>
> 复现：`NO_PROXY='*' npx tsx scripts/bench-attribution.ts --mode teach --runs 1`
> （脚本 `scripts/bench-attribution.ts` 直连 `ANALYSIS_BASE_URL`，import 生产同款
> `ATTR_SYSTEM_NOANSWER` / `attrUserPrompt`，请求参数与 `OllamaProvider` 一致；
> 只读上游模型、不写库、不启动 API）。

| 实验 | 总耗时 | TTFT | prompt / completion token | finish | 末段 |
|---|---|---|---|---|---|
| 非流式基线（生产同款，`max_tokens=1792`） | **75.8s** | n/a | 636 / **266** | `stop`（自然结束） | 完整 |
| 流式 + 核心段齐备即 abort | 78.7s | **1.0s** | n/a | 被 abort | **被截断**（`本质：…导数为零是`） |
| 冷启首次（K1.2④ 探针） | ≈110s | — | — | — | 完整 |

**由此得到的硬结论**：

1. **prefill 仅 ~1.0s（占 1.3%）**，瓶颈 100% 在 decode：266 token / ~75s ≈ **3.5 tok/s**。
   因此「prompt 瘦身 / 精简 RAG 参考块」对 p50 **最多省 1s**，不是有效杠杆。
2. **`finish_reason=stop`**：模型写完五段即自然停止，**没有跑飞**，故收紧
   `max_tokens`（现为讲解 1792 / 诊断 1536）对耗时**无影响**，只会增加截断风险。
3. **流式早停有害且零收益**：实测 78.7s > 75.8s，且把「本质」截成半句，

### 4.2 M4 达标所需的 decode 吞吐（业务指标换算）

> 目的：把「decode ≈ 3.5 tok/s × 266 token」这句工程描述，换算成**可直接拿去优化、可验收**的业务指标。
> 「瓶颈 100% 在 decode」是简写：实测 prefill 约 1.0s（占 75.8s 的 **1.3%**），
> 严格说是 **≈98.7%**；另外 bench 直连模型、**不含** API 侧的 RAG/检索/序列化固定开销。

**单次请求耗时模型**：

```
T_total = F + N / R
  F = 固定开销（TTFT/prefill + RAG + API/网络 + 解析），单位 s
  N = 本次 completion token 数（基线实测 266，finish_reason=stop）
  R = 单请求有效 decode 吞吐，单位 tok/s
  ⇒ 达标条件：p50(T_total) ≤ 30s
  ⇒ 所需吞吐：R_req = N / (30 − F)
```

**基线反推**：`D = 75.8 − 1.0 = 74.8s`，`R_now = 266 / 74.8 = **3.56 tok/s**`。

| 目标档 | 前提 | 算式 | **R 要求** | 相对现状 |
|---|---|---|---|---|
| **硬下限**（模型侧、零余量） | F=1.0s、N=266、恰好 30s | 266/(30−1) | **9.17 tok/s** | 2.58× |
| **工程目标（推荐）** | 模型侧留 25% 余量 → ≤24s | 266/(24−1) | **11.6 → 取 12 tok/s** | 3.37× |
| 生产端到端（RAG 满载） | F≈10s（TTFT 1 + RAG 8 + 其它 1） | 266/(30−10) | **13.3 tok/s** | 3.74× |
| 生产端到端 + 余量 | F≈10s、目标 ≤24s | 266/(24−10) | **19.0 tok/s** | 5.34× |

> **给优化方的单一指标**：`p50(单请求有效 decode 吞吐) ≥ 12 tok/s`（F≤6s 时可直接达标；
> 若 RAG 常年吃满 8s，则须 ≥13.3，稳妥取 ≥19）。现状 **3.56 tok/s**。
> 验收时必须同时报 `N` 的分布、`F` 的实测与 `p50(T_total)`，**不许只报 tok/s**。

**换算成另外两个杠杆**（同一公式）：

- **只砍输出长度、不动硬件**：在 3.56 tok/s 下，模型侧要 ≤30s 需 `N ≤ (30−1)×3.56 ≈ **103 token**`（比 266 砍 61%）；
  若 F=10s 则需 `N ≤ 71`（砍 73%），且会直接冲击 M3 三项齐全率，**不可单独使用**。
- **组合**：例如 `N=150 + R=8 tok/s` → `150/8 + 1 = 19.8s`（模型侧），F=9s 时端到端 28.8s 达标。

**两个必须写进结论的边界**：

1. **并发不降 p50 延迟**：M4 是**单请求** p50 延迟。在同一张受限显存卡上加并发只会分摊带宽、
   拉低单请求 R、可能让 p50 **变差**；并发解决的是吞吐/容量，不是 G1 的 M4。
   有效杠杆只有：更小模型 / 更低量化 / 更快显存与带宽 / KV cache / 投机解码 / 缩短输出。
2. **分布而非均值**：真实流量 `N` 与 `F` 都波动，G1 判的是 `p50(T_total) ≤ 30s`。
   因此验收口径应为「至少 50% 请求满足 `F_i + N_i/R_i ≤ 30s`」，并同时给出
   `p50(R_eff)`、`p50(N)`、`p50(F)`；**禁止**用平均值、缓存命中剔除分母或异步化改口径凑数。

**C. 数学可靠性专项（门禁覆盖不到的盲区）**

标杆题：$f(x)=x^3-3x$ 在 $[-2,2]$ 的单调区间与极值。

递增 $[-2,-1]$ 与 $[1,2]$、递减 $[-1,1]$；端点 $f(-2)=-2$、$f(2)=2$ 不是极值。

| 组合 | 抽样 | 结论正确 | 错误模式 |
|---|---|---|---|
| 4B + `v0.1` | 10 次 | **2/10（20%）** | 8 次统一写成「极大值 $f(1)=2$、极小值 $f(-1)=-2$」，**数值与极值类型双双写反** |

| 端到端 3 次 `correct_answer` | 3 次 | **0/3** | 全部为「极大值 $f(1)=2$、极小值 $f(-1)=-2$」 |

10/10 输出都用了 `(-\infty,-1)` 这类**全域区间**，未按题目限定到 $[-2,2]$。

### 4.6 格式契约修复与复测（2026-11-06 10:40，M4 延迟线收口 / 质量仍红灯）

#### A. 本轮边界（只做一件事）

按 §4.5-H 的优先级 ②，**只改 `apps/api/src/services/attribution/prompt.ts` 的字段解析器**：

- ✅ 改：`findLastField` 容忍「标记单独成行、冒号省略」。
- ❌ 不改：`getAnalysisProvider` / `attributionService.ts` 的 system prompt（仍是硬编码 `v0.1`，
  guard 变体**仍未接入生产**）、`promptVariants.ts`、模型与部署参数、任何线上归因内容。
- ❌ 不做：§4.5-H 优先级 ①（guard prompt 接入生产）——理由见本节 F 与下方 G。

#### B. 根因与改法

旧 `findLastField` 用 `` `${label}\s*[:：]` `` 找标记，且**切分结束位置**也只认带冒号的标记。
9B 在 `v0.1` 下高频输出 `正确推导\n$$...$$`（标记单独成行、无冒号），于是：

1. `derivation` 取不到 → `hasCore=false` → `attributionService` 返回 `incomplete`；
2. `correct_answer` 一路吃到下一个带冒号的 `常见陷阱：` → **被推导公式污染**。

改法：`buildFieldRegex(labels)` 同时识别两种形态 —— A. 原有行内带冒号；B. **整行只有标记**
（允许 markdown 强调、列表符、序号装饰），此时冒号可省。分支 B 刻意要求整行只有标记，
避免把「以下给出正确推导的思路」这类正文句子误判成标题。
**关键**：标记识别与「取下一个标记作为切分终点」必须使用**同一套正则**，
否则标题虽被认出，后续 `常见陷阱：` 仍会被吞进 `derivation`，核心三段判不全。

新增 `apps/api/src/services/attribution/prompt.test.ts`（10 条纯离线用例）：旧格式逐字段不变、
9B 无冒号样本字段互不污染、三个标题都无冒号、markdown/序号装饰、正文同名词不误判、
「正确推导 如下」不误判、真缺一段仍 `hasCore=false`、思考噪音取最后结论块、
`parseAttrTriple` 旧行为与扩展均覆盖。已加入 `apps/api/package.json` 的 `test` 显式文件列表。

#### C. 离线回放（用现成报告，改前 → 改后）

> **分组机制（须在报告中说明）**：FNV-1a 32-bit 哈希与分桶实现在 **`apps/api/src/services/rollout/cohortService.ts:25-39`**（`fnv1a32` / `bucketOf`；分组决策 `assignCohort` 见同文件 `:55-112`），按 `FNV-1a 32-bit hash(anon_user_id) % 100` **确定性分组**；`attributionService.ts` **仅调用** `assignCohort(input.anon_user_id)` 并把结果写入归因行（诊断 / 讲解两条落库路径），**不实现哈希**；`trackingService.ts` 亦按 `user_id` 服务端推导，给**所有埋点事件**写 `rollout_group`。默认 `ROLLOUT_STRATEGY='off'` → 100% `control`；`ROLLOUT_KILL_SWITCH=1` 强制全 `control`。
>
> **曝光埋点**：`rollout_exposure` **仅 `ROLLOUT_STRATEGY≠'off'` 时每次归因尝试发一次**，由 `attributionService.ts` 上报（`strategy !== 'off'` 守卫）；**默认 `off` / kill-switch 下不发曝光、曝光埋点对 `analytics_events` 零新增**（K1.4「默认零行为变化」红线）。其 `props_json` 固定为 `{group, strategy, pct, feature, feature_on}`，`context_json` 为 `{feature:'newExplanationStyle'}`，**不含 `ocr_status`**（故上传失败率不能从曝光事件计算，见 §5.3-D 与「解读约束」）。曝光计数去重的说明仅适用于**放量后的曝光数据**。
>
> **当前样本与运维口径（重要）**：默认 `off` 下所有写入恒为 `control`，013 迁移回填的历史行亦为 `control`（且默认 off 不发曝光、`analytics_events` 零新增），故**当前 §5.3 的分组 SQL 只会返回 `control` 一行**，treatment-vs-control 对比**不可判定**，报告须显式标注「**无 treatment/control 分流数据，需先放量**」，**不得据此下 GO/NO-GO 结论**。这条约束无论 off 发不发曝光都成立。
>
> **重启口径（Fix 3 后）**：**放量**（改 `ROLLOUT_STRATEGY` / `ROLLOUT_PCT` / `ROLLOUT_COHORT_ALLOWLIST` / feature 开关）须改配置**并重启 API** 才生效（其余 `ROLLOUT_*` 在 `env.ts` 模块加载时一次性快照，`getRolloutConfig()` 读快照）；**例外**：`ROLLOUT_KILL_SWITCH=1` 紧急熔断经 Fix 3 后由 `getRolloutConfig()` 动态读 `process.env.ROLLOUT_KILL_SWITCH`，**运行时即时生效、无需重启**。kill-switch 打开时全量强制 `control`，分组对比同样不可判定。G1 口径要点见 §5.3 末尾「解读约束」；原 3 条数据口径限制（第 4~6 条）已在「放量就绪」修复中解决，仍需按第 1 条等待真实放量数据。

SELECT u.exp_group,

### 5.3 当前推荐主口径（`rollout_group`，K1.4 已落地）

> 列名已确定：`attributions.rollout_group` 与 `analytics_events.rollout_group`（迁移 `013_add_rollout_group.sql`）。以下 SQL **可直接执行**，无需 JOIN、列名无需再确认。所有真实指标仍统一带 `is_mock=0 AND is_internal=0`；口径与 §2 各段保持一致，只是增加 `GROUP BY rollout_group` 做 treatment-vs-control 切分。

#### 5.3-A 归因侧：认可率 + 三项齐全率按组分段

```sql
SELECT a.rollout_group,
       SUM(CASE WHEN a.rate_action = 'approve' THEN 1 ELSE 0 END) AS approve_count,
       SUM(CASE WHEN a.rate_action IS NOT NULL THEN 1 ELSE 0 END) AS rated_count,
       SUM(CASE WHEN a.rate_action = 'approve' THEN 1 ELSE 0 END) * 1.0
         / NULLIF(SUM(CASE WHEN a.rate_action IS NOT NULL THEN 1 ELSE 0 END), 0) AS approval_rate,
       SUM(CASE WHEN (a.cause IS NOT NULL AND a.knowledge_point IS NOT NULL AND a.essence IS NOT NULL)
                   OR (a.knowledge_point_id IS NOT NULL AND a.cause_id IS NOT NULL)
                THEN 1 ELSE 0 END) AS complete_count,
       COUNT(*) AS attr_total
FROM attributions a
WHERE a.is_mock = 0 AND a.is_internal = 0
GROUP BY a.rollout_group;
-- 认可率 = approve_count / rated_count（同 §2.1，分母为 rated_count）
-- 三项齐全率 = complete_count / attr_total（同 §2.3）
-- 逐组对比 treatment vs control
```

#### 5.3-B 归因侧：p50 归因延迟按组分段

```sql
-- 主推：复用 §2.4 有序查询，仅加一行组过滤（:grp 依次取 'treatment' / 'control'）
WITH lat AS (
  SELECT attr_latency_ms AS ms
  FROM attributions
  WHERE is_mock = 0 AND is_internal = 0
    AND attr_latency_ms IS NOT NULL   -- analyzing/incomplete 不落库，天然排除
    AND rollout_group = :grp
),
cnt AS ( SELECT COUNT(*) AS n FROM lat )
SELECT :grp AS rollout_group, ms AS p50_latency_ms
FROM lat
ORDER BY ms
LIMIT 1 OFFSET ( SELECT CAST(n/2 AS INTEGER) FROM cnt );
```

```sql
-- 可选：一次出两组（需 SQLite ≥ 3.25 窗口函数；中位位置与 §2.4 的 n/2 等价）
WITH ranked AS (
  SELECT rollout_group, attr_latency_ms AS ms,
         ROW_NUMBER() OVER (PARTITION BY rollout_group ORDER BY attr_latency_ms) AS rn,
         COUNT(*)     OVER (PARTITION BY rollout_group) AS n
  FROM attributions
  WHERE is_mock = 0 AND is_internal = 0
    AND attr_latency_ms IS NOT NULL
)
SELECT rollout_group, ms AS p50_latency_ms
FROM ranked
WHERE rn = CAST(n/2 AS INTEGER) + 1
ORDER BY rollout_group;
```

#### 5.3-D 事件侧：上传失败率按组分段

> **解读约束（须随 §5.3 结果一并写入报告；1~3 为 G1 口径要点，4~6 为数据口径限制——已在「放量就绪」修复中解决，此处保留成因与仍需注意的解读约束）**：
> 1. **目前没有 treatment 样本**：生产库 `013_add_rollout_group.sql` 已应用，历史行 `rollout_group` **全部回填 `'control'`**；且默认 `ROLLOUT_STRATEGY='off'` → 100% `control`（`ROLLOUT_KILL_SWITCH=1` 亦强制全 `control`）、默认 off 不发曝光。因此**当前执行 §5.3-A~D 任何分组对比 SQL，只会返回 `control` 一行**，没有 treatment 组可对比。报告**必须标注「无 treatment/control 分流数据，需先放量」，且不得据此下 GO/NO-GO 结论**；须先放量后重新取数（**放量须改配置并重启 API；但 `ROLLOUT_KILL_SWITCH=1` 紧急熔断运行时即时生效、无需重启**，见 §5 引言「重启口径」）。该约束无论 off 发不发曝光都成立。
> 2. **曝光计数是去重的，不等于归因尝试次数（仅限放量后的曝光数据）**：§5.3-C 的 `exposure_cnt` 来自 `rollout_exposure`，其 `idempotency_key = 'rollout_exposure|<anon_user_id>|<loop_id>'` 配合 `INSERT OR IGNORE` + UNIQUE 约束，故 `COUNT(*)` / `SUM(CASE...)` 得到的是**去重后的 (user, loop) 对数**，同一 (用户, loop) 重复归因只落 1 条，**不得把曝光数当作「归因尝试次数」使用**。`attr_show_cnt` / `rate_cnt` 走 `trackingService.ingest`，幂等键为 `(user, loop, event_name, event_seq, channel)`，**去重粒度与曝光不同**，勿把本条推论到这两列。默认 `off` / kill-switch 下不发曝光、`analytics_events` 零新增。
> 3. **曝光事件不含 `ocr_status`，上传失败率不能从它计算**：`rollout_exposure` 的 `props_json` 仅含 `{group, strategy, pct, feature, feature_on}`，**不含 `ocr_status`**；对其做 `json_extract(props_json,'$.ocr_status')` 只会得到全 NULL。上传失败率**仍须按 §2.5** 用 `loop_upload` 的 `props.ocr_status='fail'` 聚合（§5.3-D 已按此实现），并沿用 §2.5 三条测量盲区；v0.1 不存在独立 `upload_fail` / `ocr_fail` 事件。全文含 `json_extract(props_json,'$.ocr_status')` 的 3 段 SQL（§2.5 / §5.2 / §5.3-D）均带 `WHERE event_name='loop_upload'`，作用域无问题。
> 4. **[已修复·放量就绪] `is_internal` 同源（原 P1：内部 / 本机流量下漏斗断裂）**：原实现中 `rollout_exposure.is_internal` 来自归因请求（服务端 `metadata.ts:37-38` 按本地回环 IP / 白名单判定 → 本机恒 1），而展示 / 评价只信前端 `ctx.is_internal`（`buildContext` 不产出该字段 → 恒 0），故 `WHERE is_internal=0` 只过滤曝光、切断漏斗。**已修复**：`trackingRoutes.ts` 把全局 `metadataMiddleware` 算出的 `req.is_internal` 作为 `serverMeta` 传给 `ingest()`，`trackingService.ts` 用它覆盖前端标记，三类埋点与归因 / 曝光同源。隔离库真实 HTTP 端到端验证（`LLM_PROVIDER=mock`、`ROLLOUT=percentage/100`）显示 `loop_upload` / `loop_attr_show` / `attr_rate` / `rollout_exposure` / `attributions` 的 `is_internal` **全为 1**；`trackingService.test.ts` 覆盖双向覆盖与「不传 serverMeta 时向后兼容」。**仍须注意**：`WHERE is_internal=0` 会把本机调试流量整体排除（这是设计意图），报告须声明只统计外部真实流量；曝光→展示转化率的分子分母去重粒度不同（见第 2 条）。
> 5. **[已修复·放量就绪] `is_mock` 同源（原 P2：Mock 归因下跨段错配）**：原实现把 `rollout_exposure.is_mock` 硬编码 0，而 `attributions.is_mock` 动态，Mock 归因下按 `is_mock=0` 过滤会剔除归因行却保留曝光。**已修复**：曝光入口按 `provider.name === 'mock'` 打初值；归因结果确定后 `alignExposureMockFlag()` 调新增的 `analyticsEventModel.markExposureMockFlag()`，把该 `(user, loop)` 的曝光 `is_mock` 对齐到归因最终值，**覆盖运行时 Mock 兜底（fallback）场景**。端到端验证中曝光与归因 `is_mock` 同为 1；单测覆盖「只改指定 (user, loop) 的曝光、不误伤其它事件」。跨 §5.3-A 与 §5.3-C 的转化率对比仍应保证同一数据口径（真实模型流量）。
> 6. **[已修复·放量就绪] 分组漂移（原 P2：刷新页面后 `user_id` 丢失）**：`trackingContext` 是模块级内存态，刷新后重置为 `user_id=''`，而 `anonUserId` 从 localStorage 恢复 → 原 `useLoop.ts` 只在新建账户分支调 `tracker.setUser(...)`，后续埋点带空 `user_id`，`assignCohort('')` 可能把同一 loop 拆两组。**已修复**：`ensureAccount()` 无论 uid 来自新建账户还是本地恢复，每次都重新 `tracker.setUser(uid, seg)`。**放量前仍建议执行** `SELECT COUNT(*) FROM analytics_events WHERE anon_user_id='' OR anon_user_id IS NULL` 作防御性预检（见附录 C 步骤 6）；归因行分组（§5.3-A / B）本就不受影响。
