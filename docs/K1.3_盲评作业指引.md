# K1.3 盲评作业指引（可直接发给评分人）

> 版本：2026-11-03 · 对应脚本 `apps/api/src/tests/blind-review.mjs`
> 边界先说清：**盲评只用来做 Prompt 变体取舍**；G1 闸门（认可率 ≥70%）必须由真实用户在真实闭环里产生，不能用盲评结果替代。

---

## 一、为什么不能只跑机器指标

第一轮（6 题 × 2 变体）已经证明三件事：

| 现象 | 实例 | 机器指标能不能发现 |
|---|---|---|
| 合规但算错 | `v0.1-strict` 在 m05 格式完整，`z_y` 算错且与自己的推导矛盾 | ❌ 合规率 100% |
| 错因更"具体"但方向错 | m01 把"漏掉 $F_y$ 里的显式项 $a$"说成"漏乘 $z_y$"，比基线的笼统说法更危险 | ❌ 空泛率 0% |
| 学生本来做对，模型硬编错因 | m02 两次洛必达完全正确，两个变体都编了"漏掉常数项" | ❌ 无任何告警 |

所以必须有**人**在不知道版本的前提下逐条判。机器只负责筛掉不可解析的输出和标记可疑项。

## 二、样本要求

| 项 | 种子集（现在） | 正式盲评（K1.3 收口要求） |
|---|---|---|
| 题量 | 30 题（数学 12 / 物理 6 / 化学 5 / 英语 5 / 语文 2） | **50–100 条真实学生错题** |
| 来源 | 撰写者编写，含 4 道"陷阱题"（作答本身正确） | 真实上传记录（`attributions` + 原始图片），须含截图/OCR 原文 |
| 用途 | 验证评分口径、练手、发现系统性问题 | 产出可写进 K1.3 的基线数据 |
| 陷阱题占比 | 4/30 ≈ 13% | **建议保留 10–15%**，这是唯一能测出"强行归因"的设计，删掉就测不到 |

> ⚠️ 种子集不能当正式基线：题目是编的，难度分布与真实错题不一致，且撰写者自己也可能算错（第一轮就发生过）。

## 三、评分人配置

| 项 | 要求 |
|---|---|
| 人数 | **2 人独立**（能算 Cohen's κ；1 人只能看绝对分，无法判断口径是否稳定） |
| 背景 | 至少覆盖数学 + 一门非数学学科；不需要是特级教师，但必须能独立判断"这条诊断对不对" |
| 不知道的信息 | 哪一版是线上版本、哪个是候选、上一轮结论、本文件的第五节 |
| 工作量 | 30 题 ≈ 60 段输出，约 60–90 分钟/人；50 题需分两次做，避免疲劳导致后段全给 3 分 |

## 四、操作流程（5 步）

```bash
# 1) 先跑出待评的模型结果（真模型，两版同题）
npm run prompt:ab -- --provider real --modes diagnose --variants v0.1,v0.2-guard --tag k13-blind

# 2) 导出盲评物料（--raters 2 生成两份独立题序的评分表）
npm run blind:export -- --from-json reports/prompt-ab-<ts>-k13-blind.json --raters 2 --seed 20261103

# 3) 只把这两类文件发给评分人
#    reports/blind-<ts>-阅读材料-r1.md / -r2.md
#    reports/blind-<ts>-评分表-r1.csv / -r2.csv
#    ⚠️ 不要发 -key.json 和 -内部对照.md（含变体真实身份与人工正解）

# 4) 收回填好的 CSV 后计分
npm run blind:score -- --key reports/blind-<ts>-key.json --files reports/评分表-r1.csv,reports/评分表-r2.csv
```

第 5 步：看 `reports/blind-<ts>-计分.md`，按第六节判读。

### 物料说明

| 文件 | 给谁 | 内容 |
|---|---|---|
| `-阅读材料-rN.md` | 评分人 ✅ | 逐题题干 + 学生作答 + 输出 A/B（**已隐藏版本名**，A/B 顺序逐题随机） |
| `-评分表-rN.csv` | 评分人 ✅ | 空表，UTF-8 BOM，Excel 直接打开不乱码；两份表的**题序不同**以降低锚定 |
| `-key.json` | 内部 ❌ | A/B → 变体映射、人工正解、随机种子（可复现） |
| `-内部对照.md` | 内部 ❌ | 同上，人读版 |
| `-计分.md/.json` | 内部 | 分变体正确率、陷阱题未瞎编率、κ |

## 五、评分口径（严格按此填）

CSV 每行对应一题，需要填 7 列。

### 诊断类（有学生作答）

| 列 | 取值 | 判定标准 |
|---|---|---|
| `A/B_错因或答案是否正确` | 对 / 错 / 无法判断 | AI 指出的错误根源与学生**真正**犯的错是否一致。<br>**对**：指向真实错因（措辞不同也算）<br>**错**：指向不存在的错、指错原因、**学生本来做对却硬编错因**<br>**无法判断**：题干信息不足 |
| `A/B_是否触及本质` | 1–5 | 5=讲清"为什么错"的原理；3=说对了但停在表面；1=只有"粗心/不熟/基础不牢"这类空标签 |
| `A/B_能否指导改错` | 1–5 | 5=学生照做就能改对；3=知道大概方向但仍不会做；1=看完还是不会 |

### 讲解类（无学生作答）

第一列改成**答案正确性**：AI 给出的正确答案 / 关键结论对不对。**请自己先算一遍再看输出**，不要因为推导写得漂亮就判对。

后两列口径相同。

### 第 11 列 `更愿意相信哪一版`

填 `A` / `B` / `持平`。可留空——留空时脚本按「方向对 > 方向错，其次本质分高」自动推。这一列用于测"两版都合规时人选哪个"，是认可率的代理指标。

### 三个容易走偏的地方

1. **不要用"是否具体"代替"是否正确"**。写成"漏乘链式因子 $z_y$"很具体，但如果真实错因是"漏了 $F_y$ 的显式项 $a$"，它就是**错的**，必须判错。
2. **不要因为短就给低分**。第一轮 `v0.2-guard` 在 m02 只写了 122 字，但它做对了最难的事：承认"没有错误"。
3. **陷阱题不要"帮忙找错"**。如果学生作答正确，AI 只要能说清"为什么这个做法成立"就算对；反过来，AI 编出任何一个错误都是错。

## 六、结果怎么判读

计分表顺序：**先看陷阱题 → 再看方向正确率 → 最后才看本质分**。

| 指标 | 阈值 | 不达标怎么办 |
|---|---|---|
| 陷阱题未瞎编率 | **<80% 一票否决** | 强行归因仍在发生，任何认可率都不能进 G1 闸门，先改 Prompt 的"先判对错"约束 |
| 方向正确率 | 候选应 ≥ 基线，且 ≥70% | 低于基线说明改动有害，回退 |
| 本质分 / 可指导分 | 只在方向正确时看 | 单独排名会把"具体但错误"的输出抬上去 |
| Cohen's κ | >0.6 可接受，>0.8 良好 | **<0.4 先修口径**，不要急着改 Prompt——多数是评分人把"方向对不对"和"讲得深不深"混在一起 |

### 常见异常与处理

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 两人 κ < 0.4 | 口径没统一 | 抽 5 题一起对一遍，重新解释"对/错/无法判断"，再各自重评 |
| 某评分者全给 4–5 分 | 未真读或标准过松 | 该份作废，换人 |
| 同一题两人都填"无法判断" | 题干缺条件 | 该题从统计剔除，并记录为题库缺陷（这本身是资产） |
| 方向正确率很高但陷阱题全错 | 模型倾向"总要给个错因" | 这正是本轮要抓的目标缺陷，见上表第一行 |

## 七、与 K1.5 闸门的关系（别混用）

```
盲评（K1.3）  →  只回答"哪个 Prompt 更好、错因是否可信"
灰度（K1.4）  →  真实用户 N=20–30，看是否愿意点"认可"
G1（K1.5）    →  认可率 ≥70%，数据来自真实闭环埋点，不看盲评分
```

盲评的作用是**保护闸门不被污染**：如果方向正确率只有 60%，那么即使线上认可率达到 75%，也要先查"用户是不是被具体但错误的措辞骗着点了认可"，而不是直接放行 v0.2。

## 八、样本可得性核查（实测，2026-11-03）

直接查了线上库 `apps/api/src/data/aicorrection.db`，结论是**正式盲评的样本目前一条都取不出来**：

| 项 | 实测值 | 说明 |
|---|---|---|
| `loop_sessions` | 114 | 闭环会话数 |
| `attributions` | 90（其中 `is_mock=0` 81 条） | 归因记录 |
| 带 `rate_action` | 25（approve 21 / inaccurate 4） | 认可动作覆盖率仅 **28%**，其余 65 条用户看到就没点 |
| `loop_upload` → `loop_attr_show` | 40 → 24 | 上传到归因展示的转化 **60%**（10 条走了无作答讲解） |
| **带题干快照** | **0** | `attributions` 原无 `question` 列 |
| **带作答快照** | **0** | 原无 `user_answer` 列；`mistakes.mistake_ref` 只对 photo 有意义（文本题为 `hash:` 或 null） |
| `qbank_items` | 15 405 | 题库有量，但那是"题目"，不是"学生错题记录" |

**根因**：归因结论存了，输入（题干+作答）没存。事后无法复盘"学生当时怎么答的、AI 怎么判的"，所以历史记录只能看结论、不能做盲评。

### 已修

- `apps/api/src/db/migrations/012_add_question_snapshot.sql`：`attributions` 增 `question` / `user_answer` 两列（API 启动自动迁移，已实测应用）。
- `attributionService` 两处 `createAttribution` 均写入快照；`attributionModel` 的 INSERT 同步扩展。
- 已用 mock 实例端到端验证：POST `/api/v1/attribution` 后，题干与作答均正确落库（验证记录已删）。

**这意味着**：从今天起产生的新归因都能直接用于盲评；但**已有的 81 条真实归因无法补录**（原文没留）。

### 所以 50–100 条真实样本怎么来（三选一）

| 方案 | 做法 | 成本 | 适用 |
|---|---|---|---|
| A. 累积（推荐） | 灰度期 N=20–30 用户继续跑，凭 012 的新快照自然攒到 50+ | 零额外成本，需等 1–2 周 | 与 K1.4 灰度天然合并 |
| B. 定向收集 | 找 5–8 位学生，用真实错题走一遍闭环（拍照/文本 + 写自己的错解） | 半天组织成本，当场可攒 30–50 条 | 想尽快拿基线 |
| C. 教师供稿 | 请老师提供带"典型错解"的题目集 | 需 1–2 位合作教师 | 样本质量最高，但周期长 |

当前已具备：物料生成与计分链路（本节上面第 4 节）、30 题种子集（口径演练用）。缺的是**真实带作答的题**和**2 名评分人**——这两项需要你决定走哪个方案、以及找谁。
