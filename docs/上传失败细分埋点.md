# 上传失败细分埋点（v0.1.x 增量）

> 日期：2026-11-05 ｜ 性质：**诊断能力增强，不改 G1/M5 闸门口径** ｜ 依赖：无下载、无模型、无外发
> 关联：`docs/k1.5-G1闸门报告框架.md` §2.5 / 附录 A；`apps/api/src/services/tracking/trackingService.ts`

---

## 1. 解决的到底是什么问题

修复前，`loop_upload` 是上传失败率的**唯一**信号，且它由客户端在**收到 200 响应后**才上报：

| 失败类型 | 修复前是否可见 | 后果 |
|---|---|---|
| OCR / 识别失败（HTTP 200，`ocr_status='fail'`） | ✅ 可见 | 计入 M5 |
| 前端校验失败（没选图 / 没填题干） | ❌ 不可见 | 用户点了提交但无任何事件 |
| 建匿名账户失败（首访 + 后端不可达） | ❌ 不可见 | 同上 |
| 传输失败（断网 / 连接被拒 / 请求超时） | ❌ 不可见 | **最需要测量的失败反而完全没数据** |
| HTTP 4xx / 5xx、200 信封 `code!==0` | ❌ 不可见 | 分母里也不存在，等于把失败「抹掉」 |
| 「识别失败」vs「请求没到后端」 | ❌ 混在一起 | 无法定位优化方向 |

因此 M5 < 10% 的分母只是「**成功的 HTTP 上传**」，天然偏低。这不是造假，但确实是**测量盲区**。

## 2. 设计原则（硬约束）

1. **M5 原口径一字不改**：`count(loop_upload where ocr_status='fail') / count(loop_upload)` 仍是 G1 的正式口径。任何"用新口径替换 M5"都必须走战略文档修订，不得在代码或报告里偷换。
2. **终态互斥**：一次上传尝试有且仅有一个终态事件——拿到 `200 + loop` 发 `loop_upload`（含 `ocr_status='fail'`）；否则发 `upload_fail`。故
   `尝试总数 = loop_upload 数 + upload_fail 数`，`失败总数 = ocr_fail + upload_fail 数`，**不会重复计数**。
3. **不新增 `upload_start` 事件**：用「终态互斥」直接得到尝试分母，避免引入第三个事件带来的漏斗断裂 / 分母漂移。
4. **零 PII / 零学生内容**：`upload_fail` 只允许受控枚举 + 数值（`http_status` / `backend_code` / 时长 / 重试次数），**禁止**写题干、作答、图片、原始错误文案。原始 `err.message` 只参与本地分类判定，不进 `props_json`。
5. **默认行为零变化**：未失败的请求只多一个可选字段 `upload_attempt_id`；服务端幂等键对既有事件逐字不变。

## 3. 事件契约

### 3.1 `loop_upload`（既有，增量字段）

```
+ upload_attempt_id?: string   // ua_<base36时间戳>_<12位hex>，仅用于关联
```
其余字段、上报时机、`ocr_status` 语义全部不变。

### 3.2 `upload_fail`（新增）

| 字段 | 类型 | 说明 |
|---|---|---|
| `upload_attempt_id` | string（必需） | 客户端尝试 ID；服务端幂等键作用域 |
| `failure_stage` | 受控枚举 | 在哪一层失败（见下表） |
| `failure_reason` | 受控枚举 | 为什么失败（见下表） |
| `src_type` / `subject` / `retry_count` / `photo_blur` | 同 loop_upload | 便于按入口切片 |
| `upload_duration_ms` | number | **实测**耗时（从提交到失败），不是 UI 硬编码值 |
| `http_status` | number? | 仅 `server_reject` / `business_error` 时有值 |
| `backend_code` | number? | 仅 200 信封 `code!==0` 时有值 |
| `loop_id` | string? | 绝大多数为空（失败时通常还没生成 loop） |

**`failure_stage`**：`client_validation` / `account_create` / `transport` / `server_reject` / `business_error` / `unknown`
（`ocr` 不由此事件产出，由 `loop_upload.ocr_status='fail'` 在看板侧合成）

**`failure_reason`**：`missing_image` / `missing_text` / `network_error` / `timeout` / `http_4xx` / `http_5xx` / `http_other` / `backend_reject` / `unknown`（`ocr_fail` 同上，看板侧合成）

**分类纯函数**：`packages/shared/src/uploadFailure.ts` → `classifyUploadError(signal)`，前后端共用、可单测。
判定优先级：业务错误码 > HTTP 响应(5xx>4xx>其他) > 无响应(超时 > 网络 > 未知)；建账户阶段的断网单列 `account_create`。

## 4. 链路与失败可达性

```
用户点提交
  └─ useLoop.upload()
       ├─ 生成 upload_attempt_id + t0
       ├─ 客户端校验失败 ──────────────→ upload_fail(client_validation)
       ├─ ensureAccount() 失败 ────────→ upload_fail(account_create / …)
       ├─ POST /upload 失败 ───────────→ upload_fail(transport | server_reject | business_error)
       └─ 200 + loop ─────────────────→ loop_upload(ocr_status=success/partial/fail)
```

**断网时 `upload_fail` 怎么发得出去？** 发不出去是正常的：SDK 的 `localStorage` outbox
（`aicorrection.track.outbox.v1`，上限 200 条）会持久化待发队列，网络恢复或下次打开页面自动续传。
这是本次必须做的配套改动，否则「传输失败」这条证据会在刷新时丢失。

**幂等**：`trackingService.buildIdempotencyKey()` 在 `context.loop_id` 为空时改用
`attempt:<upload_attempt_id>` 作作用域。否则同一用户的所有无 loop 失败事件 key 相同，会被压成 1 条。
有 `loop_id` 的事件（含新增了 attempt id 的 `loop_upload`）key 格式**逐字不变**。

**已知边界（如实标注，不掩盖）**：
- 首次访问且从未创建过账户时，`client_validation` / `account_create` 失败发生在 `ensureAccount()` 之前，
  此时 `context.user_id` 为空、`anon_user_id=NULL`（已通过「先注入 localStorage 恢复的 uid」覆盖回访用户）。
  这类事件仍可用 `upload_attempt_id` 关联，但**不可按用户/cohort 切片**；量极低，报告中单列。
- `ocr_status='fail'` 目前仍是单一桶，**未**细分「本地 OCR 失败 / 视觉模型超时 / 空结果」。
  若后续需要，须在 `ocrService` 返回受控 `ocr_fail_reason` 并写入 `loop_upload`，属另一次纯代码增强。

## 5. 消费方式

### 5.1 新接口

`GET /api/v1/dashboard/upload-failures?window_days=14` → `UploadFailureBreakdown`

```
{
  window, scope: "is_mock=0 AND is_internal=0",
  attempt_total, failure_total, attempt_failure_rate,      // 新增诊断口径
  m5: { loop_upload_total, ocr_fail, upload_fail_rate },  // G1 原口径，逐字复现
  by_stage / by_reason / by_stage_reason                  // 分层聚合（稳定排序）
}
```
前端封装：`api.dashboardUploadFailures(windowDays)`。

### 5.2 报告用 SQL（可直接执行，真实流量）

```sql
-- A. G1/M5 正式口径（不变）
SELECT SUM(CASE WHEN json_extract(props_json,'$.ocr_status')='fail' THEN 1 ELSE 0 END) AS ocr_fail,
       COUNT(*) AS loop_upload_total
FROM analytics_events
WHERE event_name='loop_upload' AND is_mock=0 AND is_internal=0
  AND ts_utc >= datetime('now','-14 days');

-- B. 尝试级诊断口径（新增，单独上报）
SELECT SUM(CASE WHEN event_name='upload_fail'
                  OR (event_name='loop_upload'
                      AND json_extract(props_json,'$.ocr_status')='fail')
                THEN 1 ELSE 0 END) AS failure_total,
       COUNT(*) AS attempt_total
FROM analytics_events
WHERE event_name IN ('loop_upload','upload_fail')
  AND is_mock=0 AND is_internal=0
  AND ts_utc >= datetime('now','-14 days');

-- C. 失败分层（定位优化方向）
SELECT json_extract(props_json,'$.failure_stage')  AS stage,
       json_extract(props_json,'$.failure_reason') AS reason,
       COUNT(*) AS n
FROM analytics_events
WHERE event_name='upload_fail' AND is_mock=0 AND is_internal=0
  AND ts_utc >= datetime('now','-14 days')
GROUP BY stage, reason ORDER BY n DESC;
```

### 5.3 解读纪律

- `attempt_failure_rate` **通常高于** M5，这不是指标恶化，而是把原本不可见的失败纳入了统计。
- 报告中必须**并列**给出 M5（闸门判定用）与 attempt 级（诊断用），并标注「口径不同，不可互相替代」。
- 若 `by_stage` 中 `transport|network_error` 占比高 → 优先查部署 / 网络 / 超时配置；
  若 `ocr|ocr_fail` 占比高 → 优先查 OCR 识别质量；二者优化方向完全不同，混在一起会误导决策。
- 本能力**不解除** G1 的其他 OPEN BLOCKER（n≥250、M4 p50≤30s），也不改变认可率 / 三项齐全率口径。

## 7. 数据主权

本改动**不引入任何新的对外网络路径**：`upload_fail` 只发到自建 `/api/v1/track`（本机）；
outbox 存浏览器 localStorage（本机）；不含题干/作答/图片/原始错误文案。
与 `docs/P0-数据主权默认外发修复.md` 的边界一致：联网检索仍默认关闭，开启需数据主体显式逐次确认。
