# K1.3 Prompt 对比 · 第一轮结论

> 时间：2026-11-03 · 提交基线：`d63aad5`
> 目的：在**只有 system prompt 不同**的条件下，判断候选 Prompt 是否真的更好；同时暴露归因质量的系统性问题。
> 注意：本轮为**内部技术对比**，不是 G1 闸门认可率。认可率必须由 50–100 条真实错题 + 专家盲评得出。

## 一、方法（为什么单独搭 harness）

线上 `/attribution` 接口同时包含 RAG 检索、联网搜索、写库、mock 兜底，变量多于一个，结果差异无法归因到 Prompt。

因此新增 `apps/api/src/tests/prompt-ab.mjs`：直连 `provider.chat()`，同一题干、同一 user 尾部（`ATTR_TAIL_*`）、同一 `maxTokens`，仅 system 不同。

```bash
npm run prompt:ab -- --provider real --variants v0.1,v0.1-strict --tag real-full
npm run prompt:ab -- --from-json reports/xxx.json   # 不调模型，重渲染报告
```

| 变体 | 合规率 | 平均耗时 | 平均字数 | LaTeX 覆盖 | 疑似空泛错因率 |
|---|---|---|---|---|---|

## 四、逐题人工核对（关键部分）

| 题 | 模式 | 人工正解要点 | `v0.1` 判定 | `v0.1-strict` 判定 |
|---|---|---|---|---|
| m01 | 诊断 | 学生漏掉 $F_y$ 中的显式项 $a$ | ✅ 准确点名"漏掉显式项 a" | ❌ 误判为"漏乘 $z_y$ 项"，并引用了错误的微分式 |
| m02 | 诊断 | **学生解法完全正确，不应归因** | ❌ 编造"求导漏掉常数项"的错因 | ❌ 同样编造错因（表述更混乱） |
| m03 | 诊断 | 换元后未同步换上下限 → 符号翻转 | ✅ 准确 | ✅ 准确（更简短） |
| m04 | 诊断 | 未比较端点（结论数值恰好对） | ✅ 准确 | ✅ 稍啰嗦但成立 |
| m05 | 讲解 | $z_x=-\frac{1}{ae^{y+az}}$，$z_y=-\frac{a+e^{y+az}}{ae^{y+az}}$ | ❌ **300s 超时**，无输出 | ❌ 合规但 $z_y$ 算错，且"常见陷阱"自相矛盾 |
| m06 | 讲解 | 条件收敛（$p=1/2$ 发散） | ✅ 正确 | ✅ 正确，且陷阱写得比基线更具体 |

判分：`v0.1` 命中 3/6，`v0.1-strict` 命中 2/6（其中 m05 为"合规但错误"，危害更大）。

## 五、四条结论

1. **不要提升 `v0.1-strict`。** 它降低了空泛率，但同时引入了"错因指错方向"的新错误（m01），属于把错误从"笼统"变成"具体的错"。
2. **合规率 ≠ 质量。** 后续盲评表必须让人读内容，机器只能用来筛掉不可解析的输出。
3. **共性缺陷（比 Prompt 微调更值得修）：作答本身正确时，模型仍会强行归因。** m02 上两个变体都编造了不存在的错误。这直接违反 `ATTR_SYSTEM` 里"如实说明、切勿臆造"的刚性条款，也违反 DLOS 的 DSR 诚实标定原则——**宁可说"未发现错误"，不可编错因**。
4. **讲解模式是超时风险最高的路径。** m05 基线 300s 超时、strict 294s / 2733 字逼近上限。当前 `ATTRIBUTION_TIMEOUT_MS=900s` 虽能兜住，但用户体验上是"转后台分析态"。需要在讲解模式加输出长度约束。

## 六、`v0.2-guard` 首轮验证（针对上面第 3、4 条）

新增变体 `v0.2-guard`，只加两条约束，不加风格要求：

1. **先判对错**：作答完全正确时，第一行必须固定为"错因：解法正确，未发现错误"，禁止把"可以更简洁/跳了步"当错因；
2. **讲解限长**：推导 ≤5 步、陷阱 ≤2 条（每条 ≤40 字）、正文 ≤600 字。

| 题 | `v0.1` | `v0.2-guard` | 判定 |
|---|---|---|---|
| m02（作答正确，陷阱题） | 85.6s / 705 字，输出里出现"等等，实际上…让我重新检查"的自我推翻噪音，终稿虽改对但形态不可用 | **50.7s / 122 字**，"错因：解法正确，未发现错误"，干净 | ✅ guard 解决"强行归因" |
| m05（讲解） | 300s 超时 / 0 字 | **105.5s / 796 字** | ✅ 解决超时与跑飞 |

**但必须如实记录：guard 没有解决数学正确性。** m05 的 `正确答案` 行给出 $z_x=-\frac{1}{e^{y+az}}$（漏 $a$）、差值 $-a$，与它自己 `正确推导` 里写的 $z_x=-\frac{1}{ae^{y+az}}$ 自相矛盾；$z_y$ 也算错。也就是说 guard 让输出更短更快，但**内容仍可能错**。

同时更正本文档初稿的一处错误：$F_y=a+e^{y+az}$（非 $a+ae^{y+az}z_y$），故 $z_y=-\frac{a+e^{y+az}}{ae^{y+az}}$，差值 $=\frac{a+e^{y+az}-1}{ae^{y+az}}$。初稿写错，已在题集 `provisional_truth` 中更正。

> 这件事本身就是结论：**连"人工标注"都要复核**，模型的"正确答案"字段更不能直接采信。K1.3 盲评必须逐条核数学，不能只看"看起来专业"。

## 七、下一轮要改什么（按优先级）

1. ~~加"先判对错"前置~~ ✅ 已由 `v0.2-guard` 验证有效（m02）；待扩样本确认无副作用后提升为线上。
2. ~~讲解模式限长~~ ✅ 已由 `v0.2-guard` 验证有效（m05：300s→105s）；同上。
3. **数学正确性（P0，新增）**：guard 证明"短"和"不瞎编"都能靠 Prompt 拿到，但**算错仍会发生**。可行方向：
   - 讲解模式增加"结论自校验"一步：算完回代原方程/取特殊值验算，不一致则重算；
   - 或在服务端对 `正确答案` 做符号验算（引入轻量 CAS 或数值回代），不一致时降级为 `analyzing` 而不是展示错误答案。
4. **扩样本到真实错题（P1）**：种子集仅 6 题且同属数学，不足以判变体优劣；需 30+ 条跨学科真实错题。
5. **`v0.1-strict` 保留但不再作为候选**，改作"负样本"记录（它把"笼统"换成了"具体的错"，比基线更危险）。

## 八、对 K1.5 闸门的含义

G1 认可率统计必须建立在"错因正确"的前提下。本轮发现两类失真风险：

- **强行归因**：用户看到具体但错误的错因，可能因"看起来专业"而误点认可；
- **正确答案算错**：讲解模式下用户更无能力判断对错，误认可概率更高。

因此盲评表必须把 **「错因方向是否正确」**（对/错/无法判断）与 **「正确答案是否正确」** 单列，不能与「是否触及本质」合并成一栏打分，否则认可率会系统性虚高，G1 闸门判定失效。
